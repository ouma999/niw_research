# Silent Attractors: Adversarial Task Design for Frontier LLM Evaluation

Research pipeline supporting an NIW proposed-endeavor evidence trail:
a task construction methodology, a reproducible evaluation harness, a
pilot task set, and a paper draft, built on the adversarial benchmark
task design work (Dynamo/Feather platform contributions).

## What is actually working right now

Everything in this repo has been run end to end in this environment
and verified:

- Both demo tasks validate (oracle passes, naive reflex fails, by a
  wide margin) -- see `data/tasks/*/tests/test_outputs.py`.
- Both demo tasks now mirror the real Dynamo task mechanisms
  (mid-year accrual freeze requiring cross-referencing a plan
  document against census data; highly-inflationary threshold
  crossing requiring cross-referencing a policy memo against
  multi-year inflation data) using entirely fictional companies,
  numbers, and data -- **not** the content of any real submitted or
  live Dynamo task. See "A note on task confidentiality" below for
  why that distinction matters.
- Each demo task ships real multi-artifact source material (a SQLite
  database plus a spreadsheet or PDF policy document), matching the
  multi-source structure of the real platform's tasks, generated by
  `solution/build_db.py` (and `build_xlsx.py` where applicable).
- The full pipeline (`src/run_pipeline.py`) runs start to finish with
  the offline mock client, producing scored results, CSV tables, and
  PNG figures.
- `paper/main.tex` compiles cleanly to a 5-page PDF with `pdflatex`.

What is **not** yet real: the pilot results in the paper are from the
offline mock client (`--provider mock`), which has no reasoning
ability and exists only to prove the wiring works. You need to run the
pipeline against real models before any number in the paper is
meaningful.

## A note on task confidentiality and the taxonomy naming

Your real accepted Dynamo tasks are live adversarial benchmark items.
Publishing their exact content (data, oracle answers) in a public
paper would leak the answer key and destroy the task's value as an
eval item going forward. The two demo tasks in this repo were rebuilt
to faithfully mirror the *mechanism* of two of your real tasks
(discussed in prior sessions) using fictional companies and numbers
throughout -- they are safe to publish. Do not substitute real task
content into this repo's task set for anything you intend to make
public.

Separately, the nine-mechanism taxonomy (`reflex_override`,
`heuristic_substitution`, `distractor_injection`,
`evidence_synthesis_gap`, `assumption_violation`, `weak_signal_fusion`,
`exhaustive_coverage_failure`, `temporal_coupling`, `staleness_error`)
is deliberately written and named independently, rather than reusing
the platform's own internal category labels verbatim. Task design
methodology and grading mechanics are the kind of thing standard
research practice treats as fair to build on and describe in your own
words -- this repo just keeps the paper's terminology as your own
original formulation throughout, which is good practice regardless and
avoids any ambiguity about attribution.

## Setup

```bash
cd niw-research
pip install requests matplotlib numpy --break-system-packages   # if not already installed
```

No API key is needed to smoke-test the pipeline:

```bash
cd src
python3 run_pipeline.py --provider mock
```

To run against real models, export the relevant key(s) first:

```bash
export ANTHROPIC_API_KEY=sk-ant-...
python3 run_pipeline.py --provider anthropic --model claude-sonnet-4-6

export OPENAI_API_KEY=sk-...
python3 run_pipeline.py --provider openai --model gpt-5

export GOOGLE_API_KEY=AIza...
python3 run_pipeline.py --provider gemini --model gemini-2.5-pro
```

Never paste an API key into a chat conversation (including this one)
-- set it only via your own terminal/shell config, and treat it as a
credential from the moment it's issued.

### Multiple trials

A single completion per task tells you almost nothing about whether a
model reliably solves it -- one lucky or unlucky response looks
identical to a stable result. Use `--trials N` to run each
(task, model) pair N times:

```bash
python3 run_pipeline.py --provider anthropic --trials 5
```

Cost scales linearly with trials (5 trials = 5x the API calls). This
produces `data/results/pass_rate_by_task.csv` and
`figures/pass_rate_by_task.png`, which is the view that tells you
whether a task is actually discriminating (e.g. 1/5 solved -- keep it)
or has been solved cleanly (e.g. 5/5 -- needs hardening before it's a
useful adversarial item, exactly like a task that clears the real
platform's difficulty gate too easily).

Each run appends/overwrites `data/results/<task_id>__<model_name>.json`
(or `__trial<N>.json` when trials > 1) with the raw response,
`data/results/scored_results.json` (parsed + scored, with a `trial`
field), and regenerates all `data/results/pass_rate_by_*.csv` and
`figures/pass_rate_by_*.png` files.

## Adding your real Dynamo/Feather tasks

**Read the confidentiality note above first.** If a task is still live
on the platform (or you're unsure), do not add its real content here
if this repo -- or the resulting paper -- will become public. Build a
fictionalized version that preserves the mechanism instead, the way
the two demo tasks do.

For tasks you do add (fictionalized or already-public/retired), each
task is a directory under `data/tasks/` with this shape:

```
data/tasks/<your_task_id>/
├── task.toml          # id, domain, difficulty, failure_family, oracle answer + tolerance
├── instruction.md      # the prompt, ending in a parseable "FINAL ANSWER: <n>" instruction
├── solution/
│   ├── solve.py         # solve() = oracle answer, naive_reflex_solve() = the trap answer
│   └── build_*.py       # optional: scripts that generate environment/data/ artifacts
├── tests/test_outputs.py  # asserts oracle passes, naive fails -- exactly like Dynamo's
│                           # oracle-passes/nop-fails validation gate
└── environment/data/    # optional: source artifacts (db, xlsx, pdf) for realism /
                          # future agentic harness use
```

Note the current harness (`model_runner.py`) sends `instruction.md` as
a single text prompt to a chat completion API -- it does not give the
model file access to `environment/data/`. If your real task is
genuinely agentic (requires opening and cross-referencing separate
files), you have two options: (a) flatten the necessary facts into
`instruction.md` as the two demo tasks do, accepting that this
understates the task's real difficulty, or (b) extend the harness to
an agentic loop with file-system/code-execution tools, which is the
"highest-value next step" noted in the paper's limitations section.

Copy the two demo tasks as templates. If a real task's answer isn't a
single number (e.g. it's a classification or structured JSON), you'll
need to extend `verifier.py`'s `extract_numeric_answer` /
`score` functions to handle that answer type -- the rest of the
pipeline (runner, tagger, stats) is answer-type agnostic.

**Target for a submittable paper: 30-50 tasks** spanning several
failure families and at least 2-3 domains, evaluated against a
representative set of current frontier models (at minimum: 2-3 model
families, ideally including a smaller/cheaper model to show a
capability gradient).

## Building the paper

```bash
cd paper
pdflatex main.tex && pdflatex main.tex   # second pass resolves references
```

Before submitting anywhere:

1. Re-run the full pipeline against real models and real tasks, and
   regenerate the figures/tables the paper references.
2. Fill in `references.bib` with real citations -- start from the
   related-work leads noted in the .bib file comments (LLM-judge
   reliability studies, adversarial/collaborative agent benchmarks,
   evaluator-validity workshops).
3. Swap `\documentclass[11pt]{article}` for the target venue's official
   style file (e.g. NeurIPS, ICLR workshop template) once you've picked
   a venue -- the content and structure carry over directly.
4. Post to arXiv regardless of workshop/conference outcome -- that
   alone is dated, public, citable evidence of the endeavor.

## How this supports the NIW endeavor statement

- A public GitHub repo with a documented, reproducible evaluation
  harness is independent, verifiable evidence of the endeavor beyond
  self-report.
- An arXiv preprint is dated, public, and citable the moment it's
  posted, independent of any acceptance decision.
- A workshop or conference acceptance (e.g. a venue focused on LLM
  evaluator/benchmark reliability) adds independent expert validation.
- The task corpus itself, expanded beyond the two demo tasks, is a
  concrete deliverable that ties directly back to the "well positioned
  to advance the endeavor" prong of the NIW statement.
